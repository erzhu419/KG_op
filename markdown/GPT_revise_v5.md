# 二、你最重视的 meta-prior 有没有保住？有没有跑偏？

## 2.1 方法中保住了，而且不只是暖启动

当前离线学习路径仍然包含：

\[
\text{历史轨迹}
\longrightarrow
\psi
\longrightarrow
\text{低阶字典与图平滑筛选}
\longrightarrow
\text{经验正交基与活跃模态}
\longrightarrow
(\mu_0,\Sigma_0,\text{残余结构}).
\]

其中，源函数先验的一项协方差为：

\[
K_{\mathrm{src}}(x,x')
=
\tilde\phi(\psi(x))^\top
\widehat{\Sigma}_0
\tilde\phi(\psi(x')).
\]

这个对象把不同策略的函数值联系起来。观察一个策略后，GP 条件化能够更新另一个策略的预测。它在方法上确实属于你说的“先学习关系，再利用关系推断”。

DCT 模板则提供另一条路径：把历史好策略转化成初始点或后续候选。**当前实现同时存在函数先验和策略模板两种迁移方式。**[正文 §3.2](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/manuscript_v2_or/sections/03_problem_and_legacy_logs.tex)

四类结构先验也都能对应到具体实现：

| 你关心的结构思想 | 当前实现 | 目前能够声称的范围 |
|---|---|---|
| 正交性 | 占用权重下的经验 Gram 白化 | 对源样本加权经验分布，在截断前成立 |
| 稀疏性、低复杂度 | 按跨任务系数信号与稳定性选择活跃模态 | 数据选择哪些方向；活跃秩 8 由设计给定 |
| 可加性、低阶交互 | 线性、二次、三角函数及预设交互字典 | 在规定字典内学习关系 |
| 低频、平滑性 | \(\psi\) 相似图上的低通筛选，以及策略上的 DCT 提案 | 图上的平滑性与时间/空间 DCT 平滑性分别发挥作用 |

**所以，从算法结构看，没有把你的原始构想删掉。**

## 2.2 但“先验表示如何产生”仍是半设计、半学习

当前的表示链大致是：

\[
x\in\mathbb R^{44\text{--}336}
\;\rightarrow\;
\psi(x)\in\mathbb R^{12}
\;\rightarrow\;
52\text{ 项字典}
\;\rightarrow\;
39\text{ 项平滑特征}
\;\rightarrow\;
8\text{ 个活跃模态}.
\]

其中：

- 12 维公共运营摘要主要由领域知识设计；
- 初始字典和允许的交互形式主要由设计者规定；
- 图筛选、白化方向、活跃模态、源均值及变异结构由数据确定。

因此，当前论文合理的定位是：

> **在给定结构假设与运营表示下，从异构历史数据学习可迁移的函数关系。**

它还不能扩展为：

> 从任意超高维坐标中，自动发现任意形式的耦合结构。

这不是要求你放弃原构想，而是准确指出这篇论文完成了原构想的哪一层。

另外，**当前并非只研究 12 维或者 13 维决策问题**。原始策略确实包含 192、240、336 维；12 维是代理模型使用的公共表示。但现有证据支持的是“具有可利用结构的数百维策略问题”，不能仅凭原始维数就宣称解决了一般超高维优化。[维数与实验定义 §6.1](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/manuscript_v2_or/sections/06_experimental_design.tex)

## 2.3 当前最需要防止的偏移，在论文论证重心上

现在最强的显著结果，主要支持认证感知搜索和完整暖配置。这容易让论文越来越围绕 EC-KG 展开，而函数 meta-prior 退成一个复杂的前处理模块。

我的建议是：

**保留 meta-prior 为主线，但把“结构已经实现”“预测有局部支持”“闭环增益仍不确定”三个层次分开。**

这比为了强调 meta-prior，强行把系统总收益都归到“学到了耦合”上，更能保护这个研究方向。

- Inventory 提供了值得重视的正向信号。
- Queueing 和 OPSD 中，来源模型组合的点估计不如同基弱先验。
- 这提示来源信息的价值取决于任务与失配条件。
- 这些结果没有证明 meta-prior 无效，也没有证明它在四域普遍有益。

当前稿已经较诚实地表达了这些不确定性。下一步需要增加解释力，而不是继续调整到某个 \(p\) 值跨过阈值。

## 3.3 “完整协方差不优于对角协方差”，不等于没有学到关系

库存预测实验中，在相同八个目标观测后：

| 模型 | 平均 Spearman 相关 |
|---|---:|
| TargetGP-RawPsi | 0.7045 |
| Scrambled source prior | 0.6519 |
| Diagonal source prior | 0.7929 |
| Full source prior | 0.7898 |

其中：

\[
\text{Full}-\text{Diagonal}
=
-0.00309,\qquad
95\%\ \mathrm{CI}=[-0.00849,0.00232].
\]

\[
\text{Full}-\text{RawPsi}
=
+0.08532,\qquad
95\%\ \mathrm{CI}=[-0.03825,0.20889].
\]

完整先验对 RawPsi 的任务胜负是 **12 胜、12 负**；因此平均相关提高，并不意味着它在大多数任务上稳定改善。这里的 RawPsi 也是公共 12 维摘要上的目标 GP，并非原始数百维坐标 GP。[库存逐任务配对结果](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/paper_artifacts/v2_or_metaprior_opsd_confirm_v1/inventory_covariance_readout.json)

但有一个对你非常重要的概念：

\[
K(x,x')
=
\phi(x)^\top\operatorname{diag}(\Sigma)\phi(x')
\]

一般仍然不为零。

**系数之间独立，不代表不同策略的函数值独立。共享基函数及其尺度本身，就能产生跨策略关系。**

因此，当前结果可以支持一种更具体的研究方向：有用的信息可能主要体现在共享函数方向、来源均值和各方向尺度，额外的非对角系数相关暂时没有显示独立收益。不能为了维护“耦合”一词，要求完整协方差必须显著胜出。

# 五、主要审稿意见二：理论现在较可信，但承担不了过强的贡献叙事

当前 SURE 参考定理的关键界是：

\[
\sup_{\delta}
\mathbb E[L(\hat\lambda)-L(1)]
\le
3+\frac{9}{2m}.
\]

在单位噪声、归一化风险的参考模型中，target-only 风险是 1。所以该界允许总风险达到：

\[
\mathbb E[L(\hat\lambda)]
\le
4+\frac{9}{2m}.
\]

例如 \(m=8\) 时，上界是 4.5625。

这个结果的意义是：

> 在所规定的参考模型中，先验失配幅度增大时，某种宽松的超额风险控制仍然成立。

它没有证明：

- shrinkage 优于 target-only；
- 当前 GP 比 LOO 更好；
- 实际部署损失受到同一界控制。

当前正文已正确承认后两类差距。我的进一步建议是：**把这个定理作为设计依据，减少它在“主要创新”中的负担。**[定理与适用范围](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/manuscript_v2_or/sections/05_theory.tex)

其余理论中，样本方差消去均值、Parseval 分解、嵌套集合的最大值单调性、二项门加 union bound，都是正确且有用的基础。但审稿人可能把它们看成支撑性推导。

Lean 验证提高了形式证明的可检查性，却不会自动证明：

- 假设符合实际算法；
- 一个结果具有足够的新颖性；
- 实验已经识别出该机制的价值。

**不需要为了 OR 再堆一组弱定理。更值得加强的是理论、方法选择与实验发现之间的联系。**

# 六、主要审稿意见三：菜单代理与实际提名的失配，已经出现了具体实例

这是我本轮独立复算中最重要的新发现。

## 6.1 一个无法靠提高积分阶数解决的状态

在 Traffic 任务 `t03` 的初始化状态中，完整候选数组给出：

| 项目 | 候选 82 | 候选 114 |
|---|---:|---:|
| 高分辨率菜单评分 | **+0.0238231** | +0.0075851 |
| 单次提名参考增益 | **−0.0220031** | **+0.0075030** |
| 是否在生产筛选名单中 | 是 | 是 |
| 生产 EC-KG 是否选择 | **是** | 否 |

候选 82 同时还是**高分辨率菜单评分的全候选最优**。

也就是说：

- 生产算法并没有因为积分粗糙而误判菜单赢家；
- 更好的单次提名候选也没有被筛选遗漏；
- 两种评分目标本身给出了不同偏好。

这里的菜单代理保留了原名单、空名单等选择权，而实际终端提名没有执行同样的菜单最大化。这会让某些“只有上行机会会被保留”的幻想收益，在实际提名规则下无法兑现。[24 状态原始候选评分](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/paper_artifacts/v2_or_eckg_sure_confirm_v1/eckg_reference_states.json)

需要严格限定这个发现：

**负值是冻结工作模型内的单次提名参考增益，不是实际仿真闭环的真实负收益。** 每个状态目前只有一次高分辨率随机化积分，也还没有给这个差值提供数值误差区间。

但这已经足以成为论文应当正面讨论的失败实例。

## 6.2 “胜过基线的次数多”，不能完全说明绝对查询质量

24 个状态里，有 3 个生产选点的单次提名参考值为负：

- 上述 `t03` 初始状态：约 \(-0.0220\)；
- `t04` 晚期状态：约 \(-1.59\times10^{-4}\)；
- `t01` 晚期状态：约 \(-1.63\times10^{-7}\)。

第三个很接近零，不能夸大。

当前论文报告 EC-KG 胜或平 SingleSlotKG 为 22/24。这一统计没有错；但在上面的 `t03` 状态，SingleSlotKG 也选择了候选 82，因此“胜或平”包含两个方法一起选到负参考增益的情况。

建议在结果中同时列出：

- 对基线的胜负；
- 相对参考最优的绝对差；
- 选点参考增益为负的次数；
- 一个具有解释力的失配实例。

这样，读者才能理解代理的收益和代价。

## 6.3 最小修改方式

我不要求你证明菜单代理永远正确，也不要求把整个终端系统重构。

建议先做：

1. 对 `Traffic t03` 初始、`Traffic t04` 晚期，以及两个晚期 Queueing 状态，预先固定少量独立 reference scrambles；
2. 只重点复核生产选点、菜单赢家、单次提名赢家等相关候选的差值；
3. 判断上述负值和排名差异是否稳定。

随后再决定：

- **保留现算法：** 把它定位为计算较快的代理，完整报告失配边界；
- **做局部修改：** 在少数入围候选上增加单次提名评分重排，或者让终端规则保留与评分一致的有限菜单。

第二种会改变算法身份，需要相应的新验证。不能把现有封存结果直接标成修改后算法的成绩。

# 七、主要审稿意见四：筛选误差已定位，不应再把精力主要放在全体升阶

晚期 Queueing 的新诊断很有价值：

- 参考单次提名最优进入生产筛选名单：**1/6**；
- 平均筛选损失：约 \(0.00045848\)；
- 平均实际查询损失：约 \(0.00045992\)。

所以，在这六个状态上，几乎全部平均查询差距已经发生在 Stage A。[修正诊断汇总](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/paper_artifacts/v2_or_eckg_sure_confirm_v1/eckg_reference_validation_corrected.json)

这轮正文已经如实报告，应该肯定。

但还需要给读者更完整的分布信息。论文所报的约 87.0%，是：

\[
\frac{\text{六个状态的平均实现价值}}
{\text{六个状态的平均参考最优价值}}.
\]

逐状态比例分别约为：

\[
38.7\%,\ 92.0\%,\ 20.0\%,\ 4.7\%,\ 93.7\%,\ 100.0\%.
\]

它们的平均约为 58.2%。两种统计都能使用，但意义不同：前者更受绝对价值较大的状态影响。

**这里不能仅凭 5/6 漏掉最优，就判定算法整体失败。** 晚期增益本来可能很小，所以绝对损失、相对损失和额外计算代价应该一起看。

下一步合理的工作是：

- 补充逐状态差值或小型分布图；
- 检查筛选为何漏掉那些高价值候选；
- 判断增加少量覆盖是否值得额外计算；
- 对关键差值做独立随机化积分复核。

继续对所有状态统一提高积分阶数，不能解决筛选已经丢掉候选的问题，也不能解决上一节的菜单目标失配。

# 八、主要审稿意见五：如果坚持 meta-prior 为第一贡献，应补一项直接的信息传播检验

这是我认为最值得新增的实验。

目前的新预测实验回答了：

> 取得相同八个目标观测后，哪些模型对一组未观测策略预测得更好？

它还没有直接回答：

> 对策略 \(x\) 的一次观测，是否因为来源中学到的关系，正确改善了对另一个未观测策略 \(x'\) 的预测？

当前正文已经承认这个边界，所以这不是遗漏披露，而是还缺一层直接证据。[预测实验说明 §7.2](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/manuscript_v2_or/sections/07_results.tex)

## 建议的最小设计

沿用现有冷配置框架，不重造系统：

| 要固定的内容 | 目的 |
|---|---|
| 相同八个初始观测 | 排除暖启动差异 |
| 相同公共表示和学习基 | 排除表示变化 |
| 相同噪声模型与候选集合 | 排除 HVD 和提案差异 |
| 预先确定 query 与 held-out policies | 避免用审计真值挑好看的关系 |
| 明确的更新前、更新后评价 | 直接测量跨策略传播 |

核心比较保留三种即可：

- 同基弱先验；
- 对角来源先验；
- 完整来源先验。

如果加入错误关系对照，应尽量保持边际尺度，避免把“均值全打乱、协方差也改变”的总破坏实验，解释成只验证某一种相关结构。

主指标预先选择一个，例如：

- 未观测策略的预测误差变化；
- 或概率预测评分的变化。

排序变化和推荐变化可以作为辅助指标。报告正迁移、负迁移和没有影响的情况。

**这个实验的目的不是让 Full 必须赢 Diagonal，而是检验从来源中学到的函数结构，是否在目标任务上产生了正确的信息传播。**

如果先用已有任务开发诊断，应将其标为探索性；若据此形成新的适用条件，再用一批有限、未参与该轮开发的任务确认。不要反复扩样直到显著。

即使最终结果仍然混合，也可以形成有价值的结论，例如：

> 来源结构在某类失配和观测稀缺条件下有用，在另一些情况下主要依赖释放与目标学习。

这比笼统宣称“四个先验在所有高维问题上都有效”更符合当前证据，也更容易成为可推广的研究认识。

# 九、应用、安全和计算成本：目前哪些边界可以接受？

## 9.1 独立终验的条件安全结论仍然成立

当前定理控制的是：

\[
\Pr\!\left(
\text{获证部署且在验证分布下不安全}
\mid\mathcal F_N
\right)
\le\delta.
\]

它依赖冻结名单、指定验证分布以及相应的独立复制条件。菜单代理的排序误差、GP 均值拟合不佳，可能降低搜索质量，但不会自动推翻这个终验结论。[终验定理](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/manuscript_v2_or/sections/05_theory.tex)

当前电网结果也应按这个边界理解：

- 完整方法 25 次获证；
- 验证池复核：0/25 点估计超限；
- 异块审计池：4/25 点估计超限；
- 其中 2/25 的区间整体高于阈值。

明确超限的两次来自同一个意大利西西里市场的两条流；另两次边界情况来自瑞典 SE_4。不能写成四个独立市场失败。[安全审计表](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/manuscript_v2_or/tables/table_verification_audit.tex)

这揭示了验证分布的外部有效性问题，不是二项定理的反例。

## 9.2 当前没有必要强制追加整套未来部署研究

三个电网池交错分配同一历史时期的块，已经被稿件说清楚。

如果本稿定位为历史数据驱动的仿真方法研究，这个边界可以保留。

如果继续主张未来真实运行风险也已受控，那就需要时间顺序明确的训练、验证和未来评价设计。增加同一历史池中的审计复制次数，不能代替这种设计。

同样，traffic 中保留不合规的 status quo 会导致 abstention 后仍不合规，当前稿已经明确报告，不能再把“没有错误认证新方案”混同于“运营始终安全”。

## 9.3 当前方法的实际计算代价，应补进论文

我从当前两批账本复算的平均在线耗时如下：

| 域 | EC-KG | SingleSlotKG | FeasibleKG | PublicPsi-TS |
|---|---:|---:|---:|---:|
| Inventory | 34.03 秒 | 10.96 秒 | 9.17 秒 | 8.70 秒 |
| Queueing | 34.10 秒 | 10.47 秒 | 8.68 秒 | 7.95 秒 |
| Traffic | 52.18 秒 | 30.35 秒 | 28.97 秒 | 28.55 秒 |
| OPSD | 32.77 秒 | 11.47 秒 | 9.80 秒 | 9.44 秒 |

对一次运行很昂贵的仿真，这些额外秒数可能可以接受；对当前较便宜的 DES，它们是明显开销。因此，建议用现有数据补一个当前方法的时间表，不需要重跑实验。[首批账本](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/paper_artifacts/v2_or_eckg_sure_confirm_v1/per_run_ledger.csv)；[后续账本](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/paper_artifacts/v2_or_metaprior_opsd_confirm_v1/per_run_ledger.csv)

另外，同样的预算上限不代表同样的实际调用数。例如 Inventory、Queueing 中 EC-KG 的实际调用数高于 SingleSlotKG。当前表已经列出这些数，解释时也应保持“损失—调用量—时间”的联合视角。

费用账本方面，这轮整体已能对上：两批当前实验合计 187,136 次搜索调用、346,644 次正式验证调用，共 533,780 次在线调用。研究审计另外统计，不能把它们混成算法在线预算。

# 十、明确需要修的技术与文字问题

这些问题应该修，但大多数属于方法说明和一致性修订，不意味着要重跑全部结果。

| 位置 | 问题 | 建议修改 |
|---|---|---|
| §3.2，白化与截断 | 写成白化坐标截断后同时用于 source fitting 和 target prediction | 实际 source fitting 使用未截断白化坐标，预测变换才截断到 \([-5,5]\)。按实际路径描述，并检查截断触发比例 |
| §3.2，二次字典 | \((z^2-1)/\sqrt2\) 被称为 Legendre | 改成二次特征或 Hermite-type 特征；不要称其为 Legendre \(P_2\) |
| §3.2，输入预处理 | 标准化 \(\psi\) 先截断到 \([-4,4]\) 的操作未充分说明 | 区分输入截断与白化后截断 |
| §3.2，HVD 基 | 将所有 \(i\le j\) 写成 \(\frac12(N_i+N_j)^2\) | 实现的对角项为 \(N_i^2\)，交叉项才为 \(\frac12(N_i+N_j)^2\) |
| §4 开头 | 称为两个 closed-form updates | HVD 的约束 NNLS 不是一般意义的闭式解，应分别描述拟合与闭式 shrinkage |
| §6，FeasibleKG 定义 | 写为 \(\Pr_n(Y_g(x)\le0)\)，容易被理解成单次不违规概率 | 实际代码计算的是工作模型下机会约束成立的后验概率，应补出 \(\alpha\) 对应的阈值 |
| EC 的 single-slot 推导结尾 | 仍有 “preventing starvation” 的过强延伸 | 改成有附加条件的单步推论，避免被理解为实际动态算法的一致性定理 |
| Lean 注释 | 仍有 “Exact Unit-Variance … Realizability” 并直接指向实际模式 | 与新正文统一，改称参考模型下的界 |

其中 FeasibleKG 的正确含义，在当前高斯工作模型下更接近：

\[
\Pr_n\!\left(
g_t(x)
\le
\Phi^{-1}(\alpha)\sqrt{\hat v_{\mathrm{buf}}(x)}
\right).
\]

**代码没有简单忽略 \(\alpha=0.05\)，需要修的是论文公式。**[先验实现](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/v2_or/priors/debiased_spectral_prior.py)；[采集函数实现](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/v2_or/acquisition/verification_kg.py)；[电子附录](https://github.com/erzhu419/KG_op/blob/dd002f49/SC-OLH-KG/manuscript_v2_or/sections/09_electronic_companion.tex)
